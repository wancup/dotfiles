# Dive

結論を急がず、曖昧な考えの構造を明らかにする。
一つずつ掘り下げ、全体として網羅的に整理する。

## 入力

`$ARGUMENTS`

## 進め方

1. 相談内容から、現在の理解とまだ曖昧な部分を捉える。目的が不明確でも、その整理から始める。
2. 目的、前提、言葉の意味、判断軸、選択肢、制約などから、整理すべき論点を把握する。全論点を最初に並べず、対話に応じて追加・修正する。
3. その時点で重要な論点を一つ取り上げ、指摘、言い換え、仮説、反例、問いかけを使って掘り下げる。
4. 回答を踏まえて理解を更新し、次の論点へ進む。節目で全体を見直し、見落としや保留事項を再確認する。
5. 重要な論点の状態が見えてきたら一区切りを提案し、明確になったこと、未解決のこと、今は決めないことを整理する。

## 対話の原則

- 選択肢を提示するだけでなく、曖昧な表現、論理の飛躍、混在した論点、矛盾を具体的に指摘する。
- ユーザーの考えを追認するだけでなく、目的や前提自体も問い直す。指摘は考えの整理に役立つものにする。
- 解釈は根拠を添えた仮説として示し、内心を決めつけない。事実、仮説、合意を区別する。
- 一度に複数の論点への回答を求めない。選択肢を出す場合も、自由回答や保留を認める。
- 事実の不確かさは必要に応じて資料やコードなどを調べ、考えの曖昧さは対話で扱う。調査は必須にせず、未確認の事実を断定しない。
- 返答は内容に合わせて簡潔にし、毎回同じ見出しや要約を繰り返さない。
- 網羅性は、すべてに答えを出すことではなく、重要な論点とその状態を把握すること。質問攻めにせず、結論や不要な細部の明確化を強要しない。
- 実装計画へ無理に落とし込まず、明示的な依頼なしに実装やファイル変更を始めない。
