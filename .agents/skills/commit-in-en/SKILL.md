# 英語でコミット

## 入力

`$ARGUMENTS`（省略可）

## 手順

1. **差分と規約を確認する**
   - リポジトリの規約、`git status`、ステージ済みの差分を確認する。
   - `git log -10 --format='%s'`で直近のメッセージ形式を確認する。prefixの有無・種類・scope・区切り方などの慣習を把握する。
   - ステージ済みの変更がなければ、報告して終了する。
   - ステージ済みの差分は`git diff --cached --binary --no-ext-diff --no-textconv`で取得する。

2. **メッセージの内容を決める**
   - 入力あり：入力を英訳する。差分と矛盾する場合は、食い違いを説明して開発者に確認し、英訳・コミットを保留する。
   - 入力なし：差分と会話から変更内容とWhyを推測して候補を作る。
   - prefixを付ける慣習があり、入力で未指定なら、差分から適切なprefixを推測して補う。
   - 指定されたprefixも慣習や差分に合うか確認する。合わない場合は開発者に確認し、候補提示・コミットを保留する。

3. **英訳を3案提示する**
   - 同じ意図を表す、ニュアンスの異なる3案を番号付きで提示する。
   - 各案の違いを日本語で簡潔に説明する。
   - prefixを含め推測した箇所を明示する。推測を含む候補すべてに全文の日本語訳を併記する。
   - なるべく一文でWhyを含め、メッセージの形式はリポジトリの規約と直近のログに合わせる。
   - 4案目として自由文で修正・相談する選択肢も提示する

4. **対話で調整し、承認を受ける**
   - 変更内容・Why・表現・prefixなどを自由文で相談・修正できるようにする。要望が曖昧なら、一度にひとつずつ確認する。
   - 修正依頼や相談には対話で応じ、内容を反映した候補を再提示する。推測の明示と日本語訳も更新する。
   - 納得できるまで調整を繰り返し、修正のたびに承認を待つ。
   - 修正・相談を伴わない候補の選択、または修正版への明示的な承認を、コミット承認として扱う。
   - 質問・相談・修正依頼だけでは承認とみなさず、コミットしない。

5. **コミットする**
   - 承認された英語メッセージをそのまま`git commit -m`に渡す。シェルに解釈されないよう安全にクォートする。
   - 成功したらコミットハッシュとメッセージを報告する。失敗したら報告して停止する。

## 制限

- ステージングは必ず開発者が行う。`git add`やステージ内容を変更する操作は実行しない。
- 通常の新規コミットのみを対象とする。`amend`・`push`などは行わない。
- パス指定や`-a`でコミット対象を変更しない。
- 失敗時にGit設定やステージ内容を変更したり、フックを無効化したりしない。
- メッセージ以外の説明・確認・報告は日本語で行う。
