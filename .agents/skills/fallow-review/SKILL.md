# Fallowレビュー

`fallow review`と`fallow security`を使い、変更差分の構造的リスクとセキュリティ上の懸念候補を日本語で整理する。

## 1. 引数の解釈

`$ARGUMENTS`を空白区切りの位置引数として解釈する。

- 第1引数がある場合: 分岐元refとして扱う
- 第1引数がない場合: `fallow review`の分岐元は自動検出に任せ、`fallow security`はプロジェクト全体を対象にする

第2引数以降は使用しない。

## 2. レビュー結果の取得

分岐元refが指定されている場合は、以下を実行する。

```bash
fallow review --base <分岐元ref> --format json --quiet
fallow security --changed-since <分岐元ref> --format json --quiet
```

分岐元refが指定されていない場合は、以下を実行する。

```bash
fallow review --format json --quiet
fallow security --format json --quiet
```

両コマンドをそれぞれ実行する。一方が非ゼロ終了しても、もう一方を省略しない。セキュリティ検出は`fallow review`に含まれないため、`fallow security`を必ず別途実行する。

終了コードだけで指摘の有無を判断せず、JSON出力と標準エラーを確認する。実行失敗、空出力、不正なJSONは「指摘なし」と扱わず、未確認の範囲と理由を報告する。

ref指定時のセキュリティ結果は変更ファイルに限定されるが、既存の懸念候補も含みうる。ref未指定時は全体解析なので、変更によって新しく発生した問題とは断定しない。

## 3. 必要時の補助チェック

以下は常時実行せず、レビュー結果や解析状況に応じて使用する。

| コマンド                                              | 使用する状況と注意点                                                                                                       |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `fallow security blind-spots --format json --quiet`   | 未解決の呼び出しなど、セキュリティ解析の盲点を確認したい場合。検出がないことだけでは安全と判断しない                       |
| `fallow health --coverage-gaps --format json --quiet` | テストから依存経路がない実行時コードやexportを確認したい場合。静的な到達関係であり、実測カバレッジやテストの品質を表さない |
| `fallow suppressions --format json --quiet`           | `fallow-ignore`による検出抑制を確認したい場合。抑制の存在だけでは不適切と断定しない                                        |
| `fallow doctor --format json --quiet`                 | 設定、依存関係、解析環境の不備が疑われる場合。プロジェクトを変更せず診断する                                               |

分岐元refが指定されている場合、`doctor`以外の補助チェックにも`--changed-since <分岐元ref>`を付ける。未指定時はプロジェクト全体が対象であることを明記する。

`hardcoded-secret`カテゴリは`security.categories.include`への明示的な追加が必要であり、標準の`security`実行だけではハードコードされた秘密情報の検出を保証しない。`include`は許可リストなので、`hardcoded-secret`だけを指定すると他カテゴリが対象外になる。カテゴリ設定は無断で変更せず、結果の解釈時にこの制約を明記する。

## 4. レビュー観点

fallowのJSON結果をもとに、以下を中心に確認する。

- 変更ファイルのうち、fallowが注目すべきと判断している箇所
- dead code、複雑度、重複など、決定的に検出できる懸念
- 影響範囲や依存関係の広がりが大きい箇所
- public API、依存関係、境界越えなど、構造上の判断が必要な箇所
- 秘密情報のクライアント流出や危険な入力処理など、`security`が検出した懸念候補と、そのファイル、位置、カテゴリ、到達経路などの根拠
- fallowが検出した内容がない場合でも、解析対象、検出カテゴリ、除外設定、未解決の呼び出しなどに問題がないか

ただし、実際の差分本文を読んだ意味的レビューは行わない。fallowの結果から言える範囲を超えて断定しない。特に`security`の検出は未検証の候補であり、脆弱性が確定したとは扱わない。入力の制御可能性やサニタイズの有無など、追加検証が必要な点を示す。

## 5. レビュー結果の出力

以下のフォーマットで日本語でまとめる。

### サマリー

構造的レビューとセキュリティチェックの結果を1〜2文で要約する。使用した分岐元ref、セキュリティの対象範囲（変更ファイルまたはプロジェクト全体）、未実施・失敗したチェックがあれば併記する。

### 注目箇所

fallowが優先的に見るべきとしているファイルや領域があれば、理由とともに箇条書きで示す。該当がなければ「特になし」とする。

### 構造的な懸念

dead code、複雑度、重複、依存関係、public API、境界越えなどの観点で懸念があれば、該当ファイルやsignal idなど、fallow出力に含まれる根拠とともに記載する。該当がなければ「特になし」とする。

### セキュリティ上の懸念候補

候補があれば、fallow出力に含まれるファイル、位置、カテゴリやIDなどの根拠と、追加検証が必要な点を記載する。秘密情報らしき値そのものは転載しない。全体解析で見つかった候補や、変更ファイル内の既存候補を、今回の変更で導入されたと断定しない。

候補がなければ「検出候補なし」とし、安全性を保証するものではないことと、`hardcoded-secret`の有効化状況などの解析上の制約を添える。実行に失敗した場合は「未確認」とする。

### 総合判定

以下のいずれかで判定する。

- LGTM: 両チェックが完了し、重大な構造的懸念や追加検証が必要なセキュリティ候補が見つからない。セキュリティの安全性を保証する判定ではない
- 要修正: dead code、複雑度、重複など、修正すべき決定的な問題がある
- 要議論: public API、依存関係、境界越えなどの設計判断、またはセキュリティ候補の追加検証が必要な問題がある
- 判定保留: 実行失敗などにより、必要なチェック結果が揃っていない

判定理由を1〜2文で添える。判定保留の場合も、取得できた結果の懸念は省略しない。
